# Билет 1. Наследование, виртуальные функции, полиморфизм

## Теоретическая часть

### 1. Как в C++ устроен механизм виртуальных функций?

Для класса, в котором есть хотя бы одна виртуальная функция (своя или унаследованная), компилятор создаёт таблицу виртуальных функций (vtable).

- **Где хранится:** vtable - это статическая структура, обычно размещается в сегменте данных или rodata. Она создаётся одна на класс, а не на каждый объект.
- **Когда создаётся:** на этапе компиляции для каждого класса иерархии. В конструкторе объекта настраивается скрытый указатель `vptr`, который указывает на vtable текущего класса.
- **Что находится:** массив указателей на реализации виртуальных функций для данного класса. Если класс переопределяет виртуальную функцию, в его vtable попадает адрес переопределённой функции; если не переопределяет, то адрес функции базового класса.
- **Как формируется для каждого класса иерархии:** для базового класса vtable содержит указатели на его реализации. Для производного класса компилятор создаёт новую vtable: для переопределённых функций свои адреса, для остальных унаследованные. При множественном наследовании может быть несколько `vptr` и vtable.
- **Вызов:** при вызове виртуальной функции через указатель или ссылку на базовый класс компилятор генерирует код: взять `vptr` объекта, перейти по индексу функции в vtable, вызвать нужную реализацию. Это и есть динамическое связывание (полиморфизм).

### 2. Зачем нужен виртуальный деструктор?

Виртуальный деструктор нужен, чтобы при удалении объекта производного класса через указатель на базовый класс (`delete p;`, где `p` имеет тип `Base*`, а указывает на `Derived`) вызывался деструктор производного класса.

Если деструктор базового класса не виртуальный, при `delete p` вызовется только `~Base()`. Деструктор `~Derived()` не вызовется. Это неопределённое поведение (UB) и потенциальные утечки ресурсов, которые освобождались в `~Derived()` (память, файлы, сокеты и т.п.).

Если деструктор виртуальный, то при `delete p` сначала вызовется `~Derived()`, затем автоматически `~Base()`.

### 3. Сравнение `dynamic_cast` и `static_cast` при преобразовании указателя вниз по иерархии

| | `static_cast` | `dynamic_cast` |
|---|---|---|
| Когда проверяется | На этапе компиляции | Во время выполнения (RTTI) |
| Проверка типа | Нет. Программист сам гарантирует корректность | Проверяет фактический тип объекта |
| Поведение при ошибке | Неопределённое поведение (UB), если объект не того типа | Для указателей возвращает `nullptr`; для ссылок бросает `std::bad_cast` |
| Требования | Работает с любыми типами | Только для полиморфных типов (есть хотя бы одна виртуальная функция) |
| Стоимость | Практически нулевая (иногда корректировка смещения) | Дороже: доступ к RTTI, обход иерархии |

`static_cast` быстрый, но без проверки. `dynamic_cast` безопасный, но медленнее и требует полиморфизма.

### 4. Разница между сокрытием имени (name hiding) и переопределением виртуальной функции

- **Переопределение (override)** - в производном классе объявлена функция с той же сигнатурой, что и виртуальная функция базового класса. Тогда при вызове через указатель или ссылку на базовый класс работает динамическое связывание и вызывается функция производного класса.
- **Сокрытие имени (name hiding)** - в производном классе объявлена функция с тем же именем, но другой сигнатурой (или не виртуальная). Она скрывает все функции с этим именем из базового класса для неквалифицированного поиска. При вызове через объект производного класса будет использоваться только функция производного класса; функции базового класса с тем же именем станут недоступны без квалификации `Base::`.

Пример, где результат разный:

```cpp
#include <iostream>

struct Base {
    virtual void f(int)    { std::cout << "Base::f(int)"; }
    virtual void f(double) { std::cout << "Base::f(double)"; }
};

struct Derived : Base {
    void f(int) { std::cout << "Derived::f(int)"; } // переопределяет f(int), но скрывает f(double)
};

int main() {
    Derived d;
    d.f(3.14);      // вызовется Derived::f(int) из-за сокрытия имени (double преобразуется в int)
    Base* p = &d;
    p->f(3.14);     // вызовется Base::f(double), виртуальная, не переопределена
    p->f(3);        // вызовется Derived::f(int), переопределена
}
```

## Практическая часть

### Задание 1. Трассировка

```cpp
#include <iostream>

struct A {
    virtual void f() { std::cout << "A"; }
    void g() { std::cout << "G"; }
    virtual ~A() {}
};

struct B : A {
    void f() override { std::cout << "B"; }
};

struct C : B {
    void g() { std::cout << "C"; }
};

int main() {
    A* p = new C;
    p->f();
    p->g();
    if (B* q = dynamic_cast<B*>(p)) {
        q->g();
    }
    delete p;
}
```

**Полный вывод main:** `BGG`

Разбор по шагам:

1. `A* p = new C;` создан объект `C`, `p` типа `A*`.
2. `p->f();` `f` виртуальная. В `C` нет своего `f`, наследуется `B::f`. Вывод: `B`.
3. `p->g();` `g` не виртуальная. Вызов разрешается по статическому типу `A*`, вызывается `A::g`. Вывод: `G`.
4. `dynamic_cast<B*>(p)` `p` указывает на `C`, который является наследником `B`, поэтому приведение успешно, `q` указывает на `B`-подобъект. `q->g();` `q` типа `B*`, `B` не имеет `g`, наследует `A::g`. Вывод: `G`.
5. `delete p;` деструктор `A` виртуальный, корректно вызываются `~C`, `~B`, `~A` (ничего не выводят).

Итог: `B` + `G` + `G` = **`BGG`**.

#### а) Что изменится, если пометить `C::g` словом `virtual`?

Вывод не изменится, останется `BGG`.

`g` в базовом классе `A` не виртуальная. Объявление `virtual` в `C` делает `C::g` виртуальной только для `C` и его наследников, но она не переопределяет `A::g`. При вызове через `A* p->g()` всё равно работает статическое связывание по типу `A*`, вызывается `A::g`. При вызове `q->g()`, где `q` имеет тип `B*`, в `B` нет `g`, поэтому также вызывается `A::g`. Виртуальность `C::g` проявилась бы только при вызове через `C*` или `C&`, но таких вызовов в программе нет.

#### б) Что произойдёт, если заменить `dynamic_cast<B*>(p)` на `static_cast<B*>(p)` без проверки на `nullptr`?

Вывод не изменится, будет `BGG`. Привод корректен в данной программе.

`p` указывает на объект `C`, который является наследником `B`. Приведение `A*` к `B*` вниз по иерархии с помощью `static_cast` допустимо, если программист уверен, что объект действительно является `B` (или его наследником). Здесь это так. `static_cast` не проверяет тип во время выполнения, но проверка и не нужна. Если бы `p` указывал на чистый `A`, то `static_cast` дал бы неопределённое поведение, а `dynamic_cast` вернул бы `nullptr`. В данном коде всё корректно.

#### в) Уберите `virtual` у деструктора `A`. Будет ли программа корректной? Что именно нарушается?

Программа станет некорректной (неопределённое поведение).

При `delete p;`, где `p` имеет тип `A*`, а указывает на `C`, вызовется только деструктор `A`. Деструкторы `B` и `C` не будут вызваны. Это нарушает правило: если объект производного класса может удаляться через указатель на базовый класс, деструктор базового класса должен быть виртуальным. В данном примере деструкторы пустые, поэтому видимых утечек нет, но формально поведение не определено стандартом C++. При наличии ресурсов в `~B` или `~C` они бы не освободились.

### Задание 2. Проектирование иерархии фигур

```cpp
#include <iostream>
#include <vector>
#include <string>
#include <cmath>

class Shape {
public:
    virtual ~Shape() = default;
    virtual double area() const = 0;
    virtual std::string name() const = 0;
};

class Circle : public Shape {
    double radius_;
public:
    explicit Circle(double r) : radius_(r) {}
    double area() const override { return M_PI * radius_ * radius_; }
    std::string name() const override { return "Circle"; }
};

class Rect : public Shape {
    double width_, height_;
public:
    Rect(double w, double h) : width_(w), height_(h) {}
    double area() const override { return width_ * height_; }
    std::string name() const override { return "Rect"; }
};

int main() {
    std::vector<Shape*> shapes;
    shapes.push_back(new Circle(1.0));
    shapes.push_back(new Rect(2.0, 3.0));
    shapes.push_back(new Circle(2.5));

    for (Shape* s : shapes) {
        std::cout << s->name() << ": " << s->area() << std::endl;
    }

    for (Shape* s : shapes) {
        delete s; // благодаря виртуальному деструктору вызывается правильный деструктор
    }
    shapes.clear();
    return 0;
}
```

#### a) Сколько раз и какие деструкторы вызываются при очистке контейнера?

В контейнере 3 объекта: 2 `Circle` и 1 `Rect`. При `delete s` для каждого объекта вызывается деструктор производного класса, затем деструктор базового:

- `~Circle()` 2 раза;
- `~Rect()` 1 раз;
- `~Shape()` 3 раза (по одному на каждый объект).

Итого 6 вызовов деструкторов (если считать и сгенерированные компилятором). Если деструкторы не объявлены явно, компилятор всё равно генерирует их.

#### б) Почему без виртуального деструктора очистка была бы некорректной?

Без `virtual ~Shape()` при `delete s` (где `s` типа `Shape*`) вызывался бы только `~Shape()`. Деструкторы `Circle` и `Rect` не вызывались бы. Это привело бы к неопределённому поведению и утечкам ресурсов, если бы производные классы имели динамические поля. Виртуальный деструктор обеспечивает полиморфный вызов деструктора производного класса.
